# Собственные обложки — реализация C, 2026-10-16

## Пользовательский сценарий

При добавлении вручную, проверке ISBN/черновика и в карточке сохранённого экземпляра доступны галерея и камера. Редактор показывает границы кадра: книжный формат 2:3, квадрат или всё фото; увеличение, сдвиг по четырём направлениям, поворот 90°, сброс обработки, отмена. Управление не требует жестов. Отмена до «Использовать фото» ничего не загружает. Ошибка обработки/загрузки сохраняет редактор открытым для повторения.

После выбора сервер возвращает asset ID. Форма передаёт его в обычный create/update или сохранённый review snapshot. Галерея/камера не изменяют глобальную обложку издания. Книга и черновик показывают собственную обложку после повторной загрузки. Можно выбрать типографическую заглушку либо вернуть автоматическое изображение исходного издания. Отсутствующее/недоступное изображение заменяется названием и автором.

## Данные и хранение

`CoverAsset`: owner, source (gallery/camera), SHA256 нормализованных bytes, JPEG MIME, width/height, byteSize, private bytes, createdAt. Asset неизменяемый; повторная загрузка одинакового нормализованного файла дедуплицируется внутри одного аккаунта. Одинаковое фото разных пользователей имеет разные ID. При дедупликации сохраняется источник первой загрузки.

Первое хранилище — PostgreSQL BYTEA: изображения остаются приватными и попадают в тот же backup, что и пользовательские данные. Это сознательный компромисс: рост базы; перед production необходимы измерение объёма, retention неиспользуемых assets и проверка восстановления backup. Сервис отделён от транспорта, возможен последующий переход к private object storage с явной миграцией. Внешние каталожные изображения не копируются.

`BookCopy.coverMode`: automatic/catalog/custom/placeholder; `coverAssetId` относится к конкретному экземпляру. Edition.coverUri хранит исходный автоматический вариант; создание принимает отдельный `automaticCoverUri`, чтобы выбранный override не терял baseline. Cover-only PATCH не создаёт новое произведение/издание. Миграция additive; старые непустые copy.coverUri переводятся в catalog, выбор пользователя и прежние миграции сохраняются.

## API

| Метод | Путь | Контракт |
|---|---|---|
| POST | /api/covers | Авторизованный multipart: file + source; возвращает только metadata |
| GET | /api/covers/:id | Metadata только владельцу |
| GET | /api/covers/:id/image | Приватные JPEG bytes, no-store, nosniff; чужой/неизвестный ID — 404 |
| DELETE | /api/covers/:id | Только неиспользуемый asset владельца; ссылка из copy/draft — 409 |
| POST/PATCH | /api/books[/id] | coverMode, coverAssetId, coverUri; create также automaticCoverUri |
| PATCH | /api/scan-drafts/:id | Те же cover-поля внутри payload с существующим CAS/revision |

Для загрузки нет URL-параметра: сервер не скачивает произвольные изображения. До буферизации guard ограничивает один instance: 30 uploads/мин на аккаунт, 2 одновременных на аккаунт, 4 глобально, bounded таблица окон; отказ 429 с Retry-After. Production-wide quota остаётся отдельной задачей. Multipart до 8 000 000 bytes, один файл, один source; JPEG/PNG/WebP. Проверяются MIME, magic bytes, успешное декодирование, до 24 MP, один кадр. Sharp применяет EXIF orientation, удаляет EXIF/GPS и прочие metadata, ограничивает 1200×1800 без увеличения, кодирует JPEG85, до 2 000 000 bytes. DB CHECK дополнительно ограничивает размеры/MIME/длину bytes. SVG/PDF/поддельные/повреждённые/слишком большие файлы отклоняются.

Проверка владельца asset выполняется в транзакции присвоения. Row lock синхронизирует присвоение copy/draft и удаление: нельзя удалить изображение во время создания новой ссылки. Удаление пользователя удаляет его assets. Получение изображения требует access token; native Image передаёт Authorization только фиксированному API origin. Web получает blob авторизованным fetch и освобождает object URL. Одновременные 401 используют один refresh, чтобы несколько обложек не выполняли конкурирующую ротацию.

## Проверки

Локальные unit-тесты используют реальные JPEG/PNG/WebP bytes, EXIF orientation/stripping, pixel-bomb, MIME mismatch, corrupt/oversize input. Shared crop tests проверяют целочисленные координаты и границы для портретных/альбомных/малых фото, масштаба и крайних сдвигов.

PostgreSQL/HTTP suite расширен настоящими multipart upload и чтением JPEG, owner A/B, дедупом, limits, metadata stripping, независимостью двух copies, cover-only edition identity, сохранением review+asset после restart, batch confirmation, reset/placeholder и protected deletion. CI обязан пройти на актуальном SHA; ссылка и результат фиксируются в Notion Development Log и PR checks.

## Отложенная приёмка и границы

По просьбе владельца от 2026-10-16 ручные Android-проверки выполняются после сборки функциональности приложения. Они не блокируют продолжение разработки и не считаются пройденными. Native permission/picker/camera/crop UX и доступность Android/iOS требуют последующей проверки. iOS JS export проверяет упаковку JavaScript; это не IPA и не проверка камеры.

Неиспользуемое после выбора фото может остаться в приватном storage, если пользователь ушёл без сохранения формы; API позволяет удалить неиспользуемый asset, автоматическая retention/управление storage — отдельная задача до production. Нет независимой офлайн-библиотеки и публичных image URLs. Live catalog success, title/author lookup, настройки стиля заглушек, общая физическая полка партии и весь D–I остаются открытыми.
